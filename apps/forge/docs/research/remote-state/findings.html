Remote state, login and cloud workers

Findings on three questions: what it takes to move forge's state to a remote database, how init should log a user in and configure a machine, and how one Overseer could run jobs on local workers or cloud Claude Code sessions while staying the only writer of state.

Question 1

Move the board, not everything

Only the durable board records belong remote. Board writes already pass through one function, so a store port is feasible. The Overseer should talk to a small backend of your own, never to the database directly.

Question 2

GitHub login, your VPS as the broker

A small service on the VPS checks the GitHub user and repository permission and issues short-lived tokens. Azure and AWS work but fit worse; GitHub alone cannot hand out secrets.

Question 3

Cloud workers are the expensive part

Nothing in the Overseer can run a job on another host today. A cloud job must come back as a pushed branch. The cloud CLI offers no event stream or stop for a daemon.

The rule that shapes all three. An agent's output is a claim; only the Overseer turns a claim into state. Otherwise a session could record "gates passed" without the gates passing. Every design choice below is tested against that rule.

State today

Everything forge persists is a file on one machine. The files fall into four kinds, and only one of them is a candidate for a database.

How writes work now

  • One funnel for the board. Every tracker write goes through writeTracker, called from two places in production code: the CLI's write opener and the Overseer's pass. Reads without a lock go through TrackerReader.[1]
  • No storage port. The format adapters write file paths directly. Outside the tracker, 99 shipping modules import node:fs, 26 of them in the Overseer.[1]
  • A file lock with takeover. The lock is a folder of exclusively created generation records. A holder is taken over when its process is gone or its stamp is older than 30 seconds.[1]
  • A journal makes a hold all-or-nothing. A hold that changes a file writes hold-journal.json first; a journal left by a cut-short hold is replayed by the next lock taker.[1]
  • Byte-level promises. Unknown keys are kept in order, an unchanged file is left untouched, and ticket and epic bodies are kept byte for byte so they can be edited by hand.[2]
  • Wake-ups come from the filesystem. The Overseer runs a pass on a 150 ms debounced watch of the data folder and the Hatch folders, plus a 30 second sweep.[1]
  • No user identity exists. There is one implicit owner. The Overseer binds to 127.0.0.1, with a bearer token for writes and a cookie from a one-time code for the Bridge.[3]

Moving state remote

The recommended shape: durable records move behind a store port; the Overseer reaches them through a backend you run; everything about processes and the machine stays where it is.

MongoDB Atlas

Atlas works as the database behind a backend. It is a poor fit when a laptop connects to it directly.

Identity-provider login needs M10

Login through an identity provider (Workforce Identity Federation) is supported on dedicated clusters M10 and above with MongoDB 7.0.11 or later. The free and Flex tiers take only passwords, X.509 certificates and AWS IAM.[4][5][6]

GitHub cannot be the provider

GitHub does not implement OpenID Connect in its OAuth flows and issues no ID tokens for users. Its OIDC tokens go to Actions jobs. A broker has to sit in between.[7]

Roaming laptops meet the IP list

A project holds up to 200 access-list entries, and temporary entries last at most 7 days. Private endpoints are not available on the free or Flex tiers.[8][4][5]

Access stops at the collection

Roles scope privileges to a database and collection. Separating boards or users inside a collection is code you write.[9]

The hosted client paths are gone

The Atlas Device SDKs were deprecated in September 2024 and removed on 30 September 2025. For the Data API, MongoDB points to a driver behind your own framework or cloud function, or a partner product.[10][11]

The driver on Bun needs a recent bson

bson 7.3.4 (5 November 2026) guards against a throw at import time in Bun, tracked as NODE-7784 and affecting 7.3.0. Pin it and test on all three operating systems.[12]

Behind a backend the objections fall away. The backend has one fixed address for the access list, holds the single database credential, and does the per-board access control. A free or Flex cluster is then enough, and the database choice becomes low-stakes.

Alternatives worth knowing

  • Supabase (Postgres). Row-level security runs inside the database, and GitHub is a built-in login provider (with your own GitHub OAuth app).[14] It could replace both the database and part of the backend.
  • Turso. An embedded replica keeps a local copy that reads locally and syncs with the cloud database; offline writes are an option.[15] Closest to today's local-file feel.
  • Cloudflare Durable Objects. Each object is single-threaded and a single point of coordination, so one object per board removes the need for a lock.[16]

Init and login

The user proves who they are to GitHub; your backend decides what that identity may do and hands the Overseer a short-lived token. No connection string is ever copied to a laptop.

Why this flow

  • Loopback with PKCE by default. The standard for native apps requires the server to allow any port on a loopback redirect, and requires public native clients to use PKCE. It ties the login to the machine that started it.[17] GitHub supports it: S256 only, and the loopback port need not match the registered callback.[18]
  • Device flow only as a fallback. It works over SSH, but the standard itself names remote phishing as its risk, and Microsoft recommends blocking it wherever possible.[19][20] On GitHub it must be enabled in the app's settings and needs no client secret.[18] The AWS CLI made the same choice: PKCE by default since 2.22.0, device code on request.[21]
  • Only the Overseer refreshes. A GitHub App user token expires after eight hours and its refresh token after six months; each refresh replaces the refresh token and the old one stops working.[22] Two processes refreshing at once would strand one, which is another reason for CLI commands to go through the Overseer.
  • Authorization from GitHub itself. The collaborators API returns a user's permission and role name on a repository, so the backend can decide per repository without a second user list.[23]
  • Where the refresh token rests. Bun has a secrets API over Keychain, libsecret and Windows Credential Manager, marked new and experimental; keytar is archived.[24] The GitHub CLI falls back to a plain text file when no credential store exists, which is the realistic behaviour on a headless Linux host.[25]

The four homes you named

Rejected outright: fetching one shared, long-lived connection string from a secrets manager after login. Revoking one person means rotating it for everyone, there is no per-user audit, and one stolen laptop exposes the whole database.

Trust boundary

Two tokens with different powers, enforced by the backend. What remains is keeping the stronger one away from a session on the same machine.

The sandbox is already the boundary

The Hatch carries no token today. A session can write only its own Hatch folder, and the Overseer takes job and role from the job record for that folder, never from the request.[26] A remote store inherits this boundary; it does not create a new problem.

Windows has no boundary

Sessions and gates run unconfined on Windows by design, so the "only its own folder" guarantee does not hold there, for today's files or for a token.[26]

Sessions already carry a credential

A session's environment is a five-name allowlist plus the Claude login variables and config folder, git configuration, and an API key under API billing.[27] The Overseer token must never join that list.

Gates run agent-written code

Build gates run confined in the ticket worktree; the merged-tree gate runs in the Airlock's own merge worktree.[27] Gate confinement must deny the token just as the session sandbox does.

Local and cloud workers

The choice can be made per job at launch. Both paths have to end the same way: commits in a worktree on the Overseer's machine, where verification, gates and landing already live.

The vendor port (AgentAdapter) only turns a request into a command line and parses events; it launches nothing, and no port exists for running a job on another host.[27]

Facts about cloud Claude Code sessions that shape the design

  • Started from the CLI. claude --cloud "task" creates a cloud session; --remote is a deprecated alias. It needs a claude.ai sign-in: API keys and Console logins are refused.[28]
  • Follow-ups are fire-and-forget. claude -p "message" --cloud <id> queues the message and exits without waiting for a reply. Stream output is not supported with --cloud <id>.[28]
  • The repository comes from GitHub. The session clones the remote at the current branch, not the local checkout. With no remote, or without the Claude GitHub App on the repository, a git bundle under 100 MB is uploaded automatically, without untracked files.[28]
  • The repository's configuration applies. CLAUDE.md, .claude/skills and .claude/agents load; hooks in .claude/settings.json and .mcp.json load in a session with one repository. The user's ~/.claude does not.[29]
  • Network and secrets are per environment. Access levels are None, Limited and Full, with environment variables, a setup script and network secrets. On Anthropic-hosted sessions a proxy swaps in the GitHub credential, so it never enters the machine.[29]
  • Moving a session works one way. claude --teleport <id> brings a cloud session to the terminal, given a clean git state, the same repository and account, and a pushed branch. The CLI has no path from local to cloud.[28]
  • Usage is shared. Cloud sessions count toward the plan's usage limits, with no separate charge for the machine.[28]
  • Long-lived tokens do not help. The one-year token from claude setup-token can only make model requests. Starting a cloud session needs an interactive claude.ai sign-in, and those sign-ins expire.[30]
  • Some organizations cannot use them. Organizations with Zero Data Retention or the HIPAA configuration cannot use cloud session features, and those with customer-managed encryption keys cannot start cloud sessions.[28]
  • Automation on a subscription needs care. The Consumer Terms forbid access "through automated or non-human means, whether through a bot, script, or otherwise", with an exception where Anthropic explicitly permits it.[41] The documentation does describe sending follow-ups "from a CI script"[28], but an Overseer that starts and steers cloud sessions all day goes further than that example.
  • A Stop hook can report back. Its input includes the last assistant message, and a hook can post to an HTTP endpoint.[31]

Order of work

  1. Worker host seam, local only.Put liveness, events, steering, resume and stop behind one interface in the Overseer, with today's Watcher as its only implementation. No behaviour changes; it is the prerequisite for any cloud worker.
  2. Store port with the file adapter.Route board reads and writes through a port at writeTracker and TrackerReader. Still files, still local.
  3. Backend and login.The service on the VPS, the GitHub App, the two token kinds, and the remote adapter. CLI commands move behind the Overseer here.
  4. Cloud worker trial.One build job through claude --cloud: pushed branch in, pushed branch out, Hatch over HTTPS, completion through a Stop hook. Measure what the missing stream and stop cost in practice before committing.
