Hephaestus, Talos and Gaia: the forge core apart from its interface[1]

1The shape

Today one process, the Overseer, does two jobs: it runs the pipeline, and it serves the interface (the Bridge page, its HTTP API, browser sessions, rendered HTML). This plan separates the two and renames the parts.

  • The forge is Hephaestus and Talos, with the CLI as its command surface. It is headless, it has a version, it owns the data model and the stored formats, and it runs the whole flow alone.
    • Hephaestus is the Overseer, renamed, without the interface. One per board. It runs the pipeline and talks to the operating system and to Talos.
    • Talos takes the Watcher's place. One per board: the commander of every agent and every other child process of that board. It starts them, keeps their event logs and reports back.
  • Gaia is the one interface server of a machine. It inventories the local forges, displays them and forwards the user's instructions. It facilitates the forges; no forge needs it.
  • One narrow path joins them: the API that Hephaestus serves, with versioned reads and one command endpoint. Gaia never touches the store. It runs the forge's CLI only for what it runs today: starting, stopping and setting up a forge. Inside the forge, the CLI and Hephaestus meet in the store.

The Bridge as a separate program goes away: its views become part of Gaia, in one design. The name Zeus is reserved for a future allocator of tickets across the forges of a team; nothing of it is built.

The monorepo holds two apps, two shared packages, and three libraries inside Gaia's page:

apps/forge/   Hephaestus, Talos, the CLI, the read and command API; the whole tracker model, the readings, the wording
apps/gaia/    the one interface: server (src/) and page (page/)
              page/lib/design-system, page/lib/flint, page/lib/brand: libraries, each behind its interface file
              page/board/: the board's views, moved from forge's Bridge
packages/forge-contracts/   the wire: the documents forge serves and the commands Gaia sends
packages/system-versions/   version comparison, for both apps and the contract
  • forge and Gaia share only forge-contracts and system-versions. Neither app imports the other. Code that belongs to an app stays in that app; code moves to packages/ only when two apps really consume it, and is generalised first.
  • The tracker model, its spec helpers, the readings (src/shared/monitor) and the refusal wording stay in apps/forge. There is no tracker-model package and no board-readings package.
  • The contract's types stand on their own and import nothing from forge's model. Forge maps its model into the contract's documents, and the contract's commands into its model, in typed adapters of its own.
  • Gaia maps each forge document into its own model at its boundary (src/adapters/forge-api) and serves its page a contract of its own. The page imports no forge code and no forge-contracts type.
  • design-system, flint and brand are libraries of Gaia's page, since Gaia is their only consumer once the Bridge is deleted. Each is a top-level folder of page/lib/ with no package.json, independent of the others and of Gaia's features, with its own specs and description. Code outside a library imports only its interface file; inside a library a file imports exactly what it needs, with no barrels. An architecture test holds this.

2Decisions

  1. The Overseer becomes Hephaestus, without the interface. Talos takes the Watcher's place.
  2. Hephaestus and Talos are the forge. They have no interface, they own the data models and the stored formats, they have a version, and they run the entire flow without Gaia.
  3. Stored formats are versioned, as they are in agent-progress.
  4. One Talos per board commands every agent of that board, in place of one Watcher per job instance. It is a separate process and outlives a Hephaestus restart. Hephaestus supports one Talos version.
  5. Talos is lightweight: it starts agents with the context it is given, and it reports questions and state back.
  6. Talos has a protocol version of its own, apart from its package version, bumped when Talos's interface changes. The handshake carries the version that Hephaestus requires. A Talos of another version quits and the right one starts.
  7. Talos quits cleanly when it has to quit: it waits for each agent's turn to end, for at most 10 seconds of real time. Losing a few turns per agent in the worst case is acceptable.
  8. Talos persists its state either way. An agent that it recorded as paused is resumed automatically.
  9. Talos holds a supervision lease of one minute, measured in real time, which Hephaestus renews every 15 seconds while its passes make progress. A Talos whose lease has not been renewed for one minute stops its agents.
  10. The lease counts the time a machine spent asleep, but sleep alone stops no agent. After a wake, Talos waits one renewal interval for Hephaestus to make contact before it stops its agents, or two where the interval is shorter than five seconds. A sleeping laptop on which nothing crashed causes no interruption and no recovery.
  11. The forge cannot ask the user anything by itself. A user question halts its ticket, is persisted so it survives a reboot, and is never decided by the forge. The forge follows a fixed, programmed workflow, and the user is a step in it. The forge keeps each question with its context, its choices and a recommendation, and Gaia shows it; the vendor's mark of the recommended choice becomes a field of the decision document, so it stays visible. The session that asked is parked and frees its slot; the answer resumes it.
  12. The forge is robust against reboots: what the pipeline decides from is persisted, not held in memory.
  13. Every start is a recovery, but recovery is not automatic: the forge makes its record truthful by itself and waits for an instruction before it starts interrupted work again.
  14. A crash is a bug. It is fixed, not retried. An unexpected error in a pass is a crash on its first occurrence. A crash of Talos stops everything of its board. A crashed forge leaves a log complete enough to trace the crash back, Gaia alerts the user, and the forge stays off until the user starts it again.
  15. A network error does not end an agent. The agent's own retry handles it; Talos has no retry of its own. When those retries run out, Talos recognises that the agent ended on a network outage and reports it, and Gaia shows it.
  16. The forge uses ports and adapters for three things: the operating system (macOS first), the agent (Claude Code first) and storage (local files first; a database later).
  17. A remote, shared setup for a team is not built. The design only keeps it possible.
  18. There is one interface server, in Gaia. Gaia inventories, displays and forwards instructions. It shows local forges only; a read-only status view of remote forges may come later.
  19. Gaia reads a local forge through a small, versioned read API and forwards instructions through the forge's command endpoint, kept beside it. Forge and Gaia stay released apart, meeting only through system versions, as the monorepo design[3] has them.
  20. A forge is self-contained. It sets its own number of agents and it comes back after a reboot by its own means. Gaia may start a forge as a facilitation, never as a responsibility. The machine-wide agent limit stays, and Gaia may offer a control for it.
  21. Gaia warns when a forge goes down.
  22. Outside Hephaestus, state changes through a command: a CLI verb, as with agent-progress, or the forge's command endpoint. Nobody hand-edits a ticket file: forge takes an edit of a ticket's content as a command. Gaia's screen for that edit comes after this run; this run builds the command and no editing screen.
  23. Intake and pipeline setup are sessions the forge hosts, and both can also be invoked as a skill in the user's own agent. They deliver files or call CLI commands.
  24. The Assistant is a switch per board, off by default. Switching it off stops a running Assistant at the end of its turn, and an incident it has not settled takes its default, with the reason recorded and shown. What it should own is decided later from accumulated data.
  25. Flint's brain is left out of the core. Flint shows only inside a forge's board in Gaia, one per forge, with no brain.
  26. Eventually, all of the user's work is done through Gaia.
  27. Gaia and the Bridge become one design and one interface, a unified whole. A single forge can be maximized, also in a browser tab of its own. Nothing is embedded by iframe.
  28. apps/forge stays the home of the core. The Bridge's views move into Gaia's page, which renders them from Gaia's own model and imports no forge code (decision 51).
  29. The lease stops agents only: an install or gate line runs to its end. A gate line or an install line runs for at most 15 minutes and is then stopped (decisions 36 and 37).
  30. An agent that crashed while the forge did not is resumed twice. After that its job waits for an instruction; nothing starts it again by itself. A user's resume gives it its two automatic restarts back (decision 40).
  31. Gaia shows the running and the newest version of Hephaestus and of Talos, and offers to restart each cleanly.
  32. Nothing that exists has to be kept. Forge runs nowhere that matters yet, so stored names, stored formats and installed surfaces change outright, and existing boards are set up anew. No older board, stored format, verb, link form or client is read or kept.
  33. A new package is an architectural decision, taken before the work starts. A ticket names the packages it may create, and a running builder never introduces one. Code moves to packages/ only when two apps really consume it, and is generalised first.
  34. No forge does this refactoring. Orchestrated Opus sessions in this repository do it, outside both trackers. The owner answers how the system behaves; the run decides the migration: where code lives, version numbers, stored formats, recordings, rule files and branches. The run may change anything in this monorepo, the rule files a person owned included, with no approval gate for a rule file.
  35. An agent that ends on a network outage, a provider overload after the retries are spent included, leaves its job waiting, never counted as a failure or a crash, and Gaia alerts the user. One control in Gaia, always clickable, resumes every job that ended this way across all forges; a job that ends on an outage again waits again.
  36. An install line is stopped after 15 minutes and ends as a bounded gate does. Every line's run time is recorded, in the measure the bound uses, and shown in the pipeline overview.
  37. The 15-minute bound of a gate line or an install line does not count a sleep.
  38. A hung Hephaestus counts as gone. After a minute without progress, Talos stops the board's agents at the end of their turn; they wait for the user's resume, and Gaia shows that the forge stopped supervising them.
  39. A crash suspected before a reboot keeps the forge off, as after a crash: Gaia alerts with the crash log, and nothing runs until the user starts the forge.
  40. A user's resume gives an agent its two automatic restarts back.
  41. resume restarts interrupted work: one job, one ticket, everything, or everything that ended on a network outage. Undoing a pause is unpause.
  42. There is no hephaestus verb and no oversee verb. forge start starts Hephaestus, and the other lifecycle verbs sit beside it at the top level (stop, restart, status, pause, unpause); stage 9 settles the exact set. Hephaestus is the component's name, not a word the user types.
  43. No forge command opens the board. The user opens Gaia and picks the forge. forge open and the progress.html stub go, and forge's help and its agents' instructions name no board page.
  44. The forge keeps an unfinished entities draft in pipeline setup. It survives a reload, the pipeline agent sees it, and Continue and Apply are refused while any refusal stands. No shared pipeline-editing package exists.
  45. A refusal reads as the forge's own sentence, the one the command line prints. Forge serves each refusal as its reason code, its structured fields and its sentence; Gaia shows the sentence.
  46. Every in-flight ticket is dropped. Both trackers stop and stay stopped until their boards are set up anew.
  47. Forge owns tickets, and Gaia is a convenience over forge. Gaia holds no ticket and writes no ticket file: every change of a ticket is a command that forge accepts or refuses.
  48. A committed ticket's content is fixed. Committed is the state in which an agent may pick the ticket up at any moment: it has passed the human review where the pipeline definition requires one, and it waits for an agent. Today's ticket status pending takes the name. From committed onward the Board refuses an edit of the ticket's content with a reason. At the commit forge keeps the content by content hash and agents build from that, so it holds also where a store lets the text change behind forge. Committed is a recorded state of the ticket, never a lock a process holds, so a crashed Hephaestus leaves nothing to release. The store's own write lock is taken over from a holder that is no longer alive, judged by the process and not by the lock's age. A committed ticket no agent has picked up can be put back into draft and is edited there. It becomes committed again by the path any draft takes: reviewed again first where the pipeline definition requires a human review for it, committed without one where it requires none. Once an agent has picked it up, its work is stopped first, by the moves the Board has today.
  49. Forge and Gaia share only forge-contracts and system-versions, and neither app imports the other. The tracker model, its spec helpers, the readings and the refusal wording stay in apps/forge.
  50. The contract's types stand on their own. Forge maps its model into the contract's documents and the contract's commands into its model in typed adapters of its own, and serves finished facts in the board document instead of the views recomputing them (section 4).
  51. Gaia maps each forge document into its own model at its boundary and serves its page a contract of its own. The page imports no forge code and no forge-contracts type.
  52. design-system, flint and brand leave packages/ once the Bridge is deleted and become libraries in Gaia's page lib/, each behind its interface file and held by an architecture test as section 1 says.

Changed or new in Hephaestus:

  • Presence. The Baton record already holds the process identity, its start stamp, the boot identity and the code version (Baton.ts). The log already holds overseer-started and overseer-stopped with reason stopped or baton-passed (apps/forge/src/lib/tracker-model/Jobs.ts:325-332), written by the Overseer before it releases its Baton (apps/forge/cli/overseer/OverseerForeground.ts:169-176, :657). What is missing is a heartbeat, and a presence record that a start reads to classify itself: no start reads the log line today.
  • Recovery on instruction. Today the Playbook resumes interrupted jobs by itself. This plan reverses that (section 7).
  • Lease renewal to Talos, every 15 seconds (section 3.2).

The HTTP server shrinks to what Gaia needs (section 8): the reads (versions, identity and presence, the documents, the event, job and gate-profile streams, job files and pictures) and the command endpoint, on the loopback address. Versions, identity and the summary are open today; the rest sits behind the token. Leaving Hephaestus, for Gaia or for nowhere: browser sessions and session codes, the Bridge bundle build, Markdown rendering to HTML, and Flint's brain.

3.2 Talos

One process per board, the commander of every child process of that board: the agents, and the install and gate lines. It is detached and outlives a Hephaestus restart. It stays lightweight and knows no vendor: Hephaestus hands it a launch plan, and Talos starts the child from it and reports back.

Responsibility Today, in each Watcher (src/lib/watcher/)
Start each child from the launch plan it is given, in a process group of its own One Watcher process per child (Watcher.ts, WatcherLaunch.ts)
Append every line a child writes to its standard output to that child's event log, synced to disk when a client asks for the durable entries and at the close events-<instance>.ndjson
Report each child's state and an agent's question to Hephaestus State frames; Hephaestus reads the question out of the event log
Pass input to an agent: a message, an answer, an interrupt write frames
Answer the standing replies of a launch plan: it refuses every tool-permission request but the question tool Launch file, rendered by ClaudeCodeAdapter.ts
Recognise the endings a launch plan names, first of all an ending on a network outage, and report them Does not exist: the Overseer's stream mapper reads a budget stop, a rate limit and a refused key, and every other failed result is one generic failure
Stop a child's process tree and record its end Watcher.ts
Persist its state: every child, its process identity and its status A claim file per Watcher

What changes against the Watcher:

  • One commander in place of a fleet. Today each job instance has its own Watcher, started from a bundle pinned to its code version, and the Overseer keeps reading Watchers of older protocol versions through a legacy reader until they end. All of that goes. Hephaestus speaks to exactly one Talos, at exactly one protocol version.
  • A protocol version of its own, bumped by hand when Talos's interface changes. The first frame of the handshake carries the version that Hephaestus requires, and that frame never changes shape, since it is how two versions learn that they differ. On a mismatch, in either direction, Talos quits cleanly, and Hephaestus, which has the current code, starts the right Talos. A downgrade is covered by the same rule. A change inside Talos that leaves its interface alone restarts nothing by itself: Gaia shows the running and the newest version, and the user restarts Talos cleanly from there (section 8).
  • A clean quit. Talos asks each agent to stop at the end of its turn, waits at most 10 seconds of real time, and then stops what is still running. A line is stopped at once and run again later. The worst case is a few lost turns per agent.
  • Persisted state. Talos records each child's status on disk whatever happens. An agent recorded as paused by a clean quit is resumed automatically through the new Talos, under the usual rules for slots and the usage limit. This is workflow: it is never counted as a crash and it waits for no instruction. The same record is what lets Hephaestus find and stop the orphans of a Talos that crashed.
  • A crash of Talos stops everything. Every child of the board stops or is orphaned. Hephaestus stops the orphans from the record, marks their jobs interrupted, writes the crash log and stops: a bug, and the forge stays off.

The supervision lease. Today the Watcher has no check that an Overseer is alive, so an agent whose Overseer is gone runs on with nobody routing its questions, watching its spend or noticing that it hangs. With the lease, a Talos whose lease Hephaestus has not renewed for one minute stops its agents, with the clean quit above. Hephaestus renews only while its passes make progress, so a hung Hephaestus counts as gone. Their jobs count as interrupted and wait for the user's resume; they are not paused, and Gaia shows that the forge stopped supervising them. Talos itself stays, and waits for a Hephaestus. The lease stops agents only: an install or gate line runs to its end, and is stopped after 15 minutes, a sleep not counted.

A naive lease makes a healthy forge stop its own agents. The lease is safe only with all of this:

  • A wake that is not an expiry. The lease runs on the wall clock, so after a sleep it has lapsed on paper, for a Hephaestus that is alive as much as for one that is gone. Talos therefore never stops its agents on the first look after a gap in its own running. It gives Hephaestus one renewal interval to make contact, or two where the interval is shorter than five seconds. The interval is 15 seconds. A renewal arrives: nothing happens. None arrives: Hephaestus is gone, the sleep counted, and Talos stops its agents. Talos sees the gap by itself, as two of its own timer ticks that lie far apart, so a suspended process is covered the same way.
  • An end of its own. Today a Watcher that is gone while its job runs with no result is recorded as agent-crashed or watcher-lost, and a session that exits cleanly with no report ends its job as failed. Two counted crashes (agent-crashed, watcher-lost) back to back on jobs of different tickets, with no verified ending between them, pause the board with an outage decision. A lease end and a clean quit each need an end reason and an interruption cause of their own that is not counted as a crash.
  • Renewal that only progress earns. Git runs synchronously with no timeout (GitProcess.ts), a worktree add and the landing fast-forward among it, so a timer on Hephaestus's event loop does not fire during them. Renewal stands for progress, so it cannot run apart from the loop: every synchronous step is bounded well below the lease, and the pass hands every gate line to Talos and carries on rather than waiting through it.
  • Margin through a Baton pass. The whole pass may take about 150 seconds (BATON_PASS_OUTCOME_TRIES), and after the release there is a wait of up to 60 seconds, the length of the lease, with no clear renewer. The successor renews from the moment it takes the Baton.
  • No vendor in Talos. The request to stop at the end of a turn and the interrupt are a vendor's input lines, so they arrive in the launch plan like a standing reply. So do the patterns of the endings that Talos recognises.
  • What a stop leaves behind. An agent stopped in the middle of a git command leaves an index.lock that only the worktree repair removes today. A resume after a stop has to clear it.

Recognising an ending on a network outage. Claude Code retries a failed call ten times by default and writes a line for each retry. When the retries run out, its closing result line is marked as an error and carries, as fields, that the cause was an API error and either that the host could not be reached or the status the server answered with (a 5xx or a 529). The agent adapter renders these as patterns in the launch plan, and Talos matches them on the fields of the child's own lines, never on free text, which a model can imitate. Talos reports the ending under a name of its own, so the job is not counted as failed or crashed. Today's standing replies compare only texts and booleans, so the patterns also need numbers and the count of retry lines.

3.3 Processes on a machine

  • Hephaestus keeps one loopback port, for reads and commands. The bearer token and the Host and Origin guards stay. No browser reaches it: Gaia's server is the only client, so the browser sessions and the page's content security policy leave with the Bridge.
  • Talos and its children outlive a Hephaestus restart, for up to the lease. They do not outlive a change of Talos's protocol version: that is a clean quit and an automatic resume.
  • Not every child is under a Watcher today. The Overseer spawns merged-tree gates, gate-profile runs and pipeline checks itself, each in its own process group, and keeps the set of them in memory. They die or are orphaned with it. They go under Talos with every other child (section 7).
  • Machine-wide state stays what it is today: files under the monitor folder with no process behind them (slots, the usage marker, the agent limit, the registry). Each forge enforces them on itself. Nothing of it moves into Gaia.

3.4 The CLI

The CLI is the command-line face of the forge's contract and stays a first-class surface, also when the user no longer types it:

  • the user, or a skill in the user's own agent, runs a verb and it writes through the store;
  • an agent hosted under Talos runs the same verb, which relays through the Hatch and passes the Bouncer's role policy;
  • machine setup (init, update, the login item, the machine limit) stays CLI, and Gaia forwards to it as it does today.

Rule: outside Hephaestus, state changes only through a command. No skill and no agent writes a record file itself. This is close to today: the build and review prompts carry the ticket's text and forbid editing the ticket file, the product owner files through verbs, and the forge-po skill forbids writing under the data folder with a file tool.

The CLI must also carry everything a forge needs with Gaia closed: showing that a forge is off after a crash, with its crash log, starting it again and resuming interrupted work.

4The store and the contract

The forge has one contract with three parts. It is shaped so that it can cross a network later:

  • Commands in. File a ticket, answer a question, change the pipeline, stop the forge, resume a ticket. One service already applies 76 command kinds[2] for the CLI, the Hatch and the HTTP endpoint alike (src/services/control/). Outside Hephaestus a command is a CLI verb or a call to the command endpoint; both reach that one service.
  • Documents out. The board, a ticket, a job's progress, the forge's presence. Hephaestus assembles them and serves them over the read API, so derived state is built once, on the forge's side. This is what the Overseer does today for the Bridge. The board document carries finished facts that no client recomputes: attention entries with a typed target, worded notices and warnings, today's figures, open decisions in answering order, the moves and controls each ticket and job offers, resolved priority, stop holds, repeat-review facts, effective pipelines per entity, the unfinished entities draft with its refusals, limits and defaults. Each refusal arrives as its reason code, its structured fields and the sentence the command line prints.
  • A subscription to changes: the event and job streams of the read API.

The store sits inside the forge, behind a port that the CLI and Hephaestus use in-process:

  • Local adapter, built now: on files. It wraps today's tracker stores, the tracker lock and the single hold of writeTracker. It is the only code that names the path of a record. It keeps a committed ticket's content by its hash, and its lock passes to another writer only once the holder's process is gone (decision 48).
  • Remote adapter, not built: a client of a forge's API. The forge behind it owns the database; no client holds database credentials, and validation runs in one place.

One limit of this port: Hephaestus's own pass is not made of commands. It changes the board directly inside one hold (endJob, interruptJob, openIncident) and runs git inside that hold. So the port has two faces: commands for the CLI, and a board transaction for Hephaestus. A remote adapter cannot carry a hold that spans a git fast-forward; the remote future needs that pass redesigned, which this plan does not do.

Because Hephaestus serves the documents, fields that exist only in its memory (notices, the runtime state, the quiet counts) reach a reader, and no outside process reads the board's files. The Overseer's own reader of the board state takes no lock today (docs/reference/overseer-api.md), so a served document can still show a change half written.

What stays outside the store, under the operating system port, because it is local by nature: worktrees and the agent's working tree, Talos's launch files, sockets and event logs, slot files, and the vendor's configuration files. A reader gets a job's live output from the read API's job stream, never by knowing where an event log is.

Consequences:

  • Hand-editing stored records ends. It overturns today's local rule that tickets are hand-edited between runs[4]; an edit of a ticket's content is a command, refused from the moment the ticket is committed (decision 48). This run builds that command and no editing screen in Gaia (decision 22).
  • Version. The read API keeps the system versions and the compatibility registry it has today, so an endpoint can be served at two versions side by side. The stored formats keep their own versions inside the local adapter.
  • packages/forge-contracts already holds 9 command kinds, the summary and monitor documents and the versions, and Gaia's server imports it. The board and ticket documents that the Bridge's views read are not in it. They join it with types of their own that import nothing from forge's model, and forge fills them in typed adapters of its own; adding them is a change of the system version.
  • Gaia's commands stay under the system versions. The command endpoint keeps what it has today: the token, and the refusal of commands while an install change holds launches. The contract package holds 9 of the 76 command kinds; the board's command kinds join it with payload types declared in the contract, which only adds and so raises the minor version. Forge maps each command into its model.

6The user in the workflow

The forge never decides a user's question. It records the question and moves on.

  • A question parks its job. The forge keeps the question with its context, its choices and a recommendation, and Gaia shows it to the user. The session holds no slot, the ticket shows that it waits for the user, and the other tickets continue. An answer, written as a command from Gaia or the CLI, resumes the session.
  • Two scopes of halt, both persisted. A question, a conflict or a review outcome halts one ticket. A refused API key, a reached budget or an install mismatch halts the board, as today.
  • Planned waits are not halts. A usage limit that resets at a known time, a free slot, an answered question: the workflow continues by itself when the condition clears.

7Interruption and recovery

Where the code stands. Much of this exists, and it is automatic today:

  • interrupted is a job state with eight causes, among them watcher-lost, agent-crashed, reboot, usage-limit, answer-delivery and handoff-red.
  • At start, Regrouping contacts every live Watcher, stops the orphans of a dead one, and records a foreign boot as the cause reboot. The boot identity (kern.bootsessionuuid on macOS, boot_id on Linux) is already stored in the Baton, the Watcher record and the slot files.
  • The Playbook then resumes by itself: a crash up to JOB_RESUMES_BEFORE_FRESH times, a reboot, an answer delivery or a usage limit whatever the count. A real-system spec covers the crash, reboot and update matrix (CrashMatrix.integration.spec.ts). A paused board holds new launches only, never a resume (apps/forge/src/lib/tracker-model/Playbook.ts:770-771).

So recovery on instruction, and no retry after a crash, fill no gap. They reverse tested behaviour, in every project that runs forge. Since nothing that exists has to be kept, the change is made outright.

Every start is a recovery. There is no special shutdown path to trust: a stop is treated as if the power went out, and a start reads the store and continues from it.

Recovery has two halves.

  • Reconcile, automatic. Hephaestus makes the record truthful: a job with no live Talos is marked interrupted, a landing that did complete is recorded, dead slots are released, orphaned process groups are stopped. It starts no work.
  • Resume, on instruction. Resuming a session, running a gate line again or retrying a merge waits for the user: one instruction for a ticket, or one for everything interrupted. job-lost and resume-failed exist as incident kinds today, with fresh and park among their moves.

Which interruptions wait for an instruction has to be listed, because "interrupted" covers routine workflow too:

Cause Today In this plan
answer-delivery, handoff-red, usage-limit Resumes by itself Unchanged: these are steps of the workflow
Paused by a clean quit of Talos for a new protocol version Does not exist Resumes by itself: a step of the workflow
reboot, a stop on purpose, a lease end, an ending on a network outage A reboot resumes by itself. A stop on purpose interrupts no agent: each Watcher is detached and the next start attaches it (apps/forge/src/services/overseer/Regrouping.ts:223-244), and stop --now stops only install and gate Watchers (apps/forge/src/services/overseer/WatcherFleet.ts:340-365). A lease end does not exist, and a session that ends on a network outage ends its job as one generic failure Waits for an instruction. Gaia alerts on an ending on a network outage, and one control in Gaia resumes every job that ended this way, across all forges
agent-crashed, watcher-lost (the agent's side died, the forge did not) Resumes twice, then starts fresh Resumes twice, then waits for an instruction. A user's resume gives it its two automatic restarts back
authentication-failed, forced-stop-refused Does not resume by itself: a refused key opens a board decision that holds every launch, and a refused forced stop never resumes Unchanged
The forge crashed: Hephaestus, or Talos A crash of the Overseer interrupts no agent: its Watchers run on and the next start attaches them (apps/forge/src/services/overseer/Regrouping.ts:223-244) A bug: the forge stays off until the user starts it again

What kind of start it is is recorded, because only one kind is a bug:

Evidence at the start Meaning What follows
A Baton pass completed on record A handover, not a stop Nothing is interrupted
A stop completed on record Stopped on purpose Interrupted tickets wait for an instruction
The boot session differs from the one in the Baton, and the last heartbeat lies close before the new boot The machine went down Interrupted tickets wait for an instruction
The boot session differs from the one in the Baton, and the last heartbeat lies long before the new boot A crash suspected before a reboot As after a crash: the forge stays off, Gaia alerts with the crash log, and nothing runs until the user starts the forge
Same boot session, neither on record The forge crashed A bug. The forge stayed off until this start, which the user made, and its interrupted tickets wait for an instruction. The crash log is kept (active jobs and their steps, the tail of the log, the uncaught error where there was one)

Known misreadings of this table, not solved here: a stop on record followed by a wedged process that is killed reads as "on purpose" and hides a hang; a kill by the user or by the operating system for memory leaves the forge off as a bug; the heartbeat's staleness against the boot time only narrows a crash followed by a reboot, which is the usual path on a laptop.

What reconcile cannot see today. Merged-tree gates, gate-profile runs and pipeline checks are children of the Overseer itself. On disk they leave a gate slot that names the Overseer's process and counts as free once that process is gone, and, for profile runs and pipeline checks, a board record and a worktree that the next start marks stopped and removes without stopping the process. After a crash the next Hephaestus can gate a worktree again while the orphan still runs. They move under Talos, whose persisted record names every child.

Failure handling in one list.

  • Network trouble: the agent's own retry. When the retries run out, Talos reports an ending on a network outage, the job waits and is not counted as failed or crashed, and Gaia alerts the user. One control in Gaia resumes every job that ended this way, across all forges; a job that ends on an outage again waits again.
  • Usage limit, parked question, busy slot: planned waits that end by themselves.
  • Machine down, or stopped on purpose: reconciled; interrupted tickets wait.
  • Forge crash, or a crash suspected before a reboot: a bug, with a crash log, an alert in Gaia and at the CLI, and no retry: the forge stays off until the user starts it again.
  • Agent crash, the forge still up: resumed twice, then it waits for an instruction; a user's resume gives it its two automatic restarts back.
  • Hephaestus silent or without progress for the lease: it counts as gone. Talos stops its agents at the end of their turn; they count as interrupted, not as crashed, wait for the user's resume, and Gaia shows that the forge stopped supervising them.
  • An install or gate line past 15 minutes, a sleep not counted: stopped, and it ends as a bounded gate does.
  • Talos at another protocol version: a clean quit, the right Talos starts, and the paused agents resume by themselves.
  • Talos crash: a bug, like a crash of Hephaestus. Everything of the board stops and the forge stays off.
  • A pass that fails on an expected condition, for example because another process held the lock past its five seconds: retried at the next wake-up today. It is neither a crash nor an interruption and needs its own name. An unexpected error in a pass is a crash on its first occurrence.

Retrying an expected condition a counted number of times is workflow. Retrying after something that should never happen hides it.

What must be persisted is known in part. Held only in memory today: the event replay buffer, the pass state and fingerprint, the merge-forecast and main-line caches, the install-watch answer, the quiet-job counts, the Assistant's quiet watch, the notices and the runtime state, and the in-process gate children. Every Airlock phase is written in a hold of its own, so a stop leaves the slot in its last written phase and the rerun of that phase is safe or detects that it was done (stage 0 plan, table B). Three steps are not redone: the landing journal line after the fast-forward, the release cleanup after the landing hold, and the restore of the worktree's tip before freeSlot's hold.

8Gaia

Gaia inventories, displays and forwards. The test for anything proposed for Gaia: does every forge still do its full job with Gaia closed?

Gaia does How

How Gaia reaches a forge today, in three ways. It runs the forge's CLI (start, stop, init, update and the like), which stays. It embeds each Overseer's Bridge in an iframe, with session codes, the embed message channel and the frame-ancestors record: all of that goes. And it calls the Overseer over HTTP: versions, identity and the summary with no token, and with the token the monitor snapshot and stream, commands (which also start and stop Flint's brain) and session codes. The reads and the command call stay, and the session codes go with the iframe.

What the API keeps, because the views use it today: the board state, the event stream, the job transcript and gate-profile streams, job files (the report, the gate log), pictures and their upload, the summary and the monitor snapshot, identity and versions, the command endpoint and the nudge. What it loses: the session routes, the page itself and Flint's ask route. forge open and the progress.html stub go rather than find a new target, since a forge may not name Gaia (architecture/ClientNames.spec.ts): forge's help and its agents' instructions name no board page.

What this path gives and costs:

  • Two programs, released apart. Forge and Gaia stay released apart and meet through system versions; Gaia keeps supporting one forge version and testing against recorded answers of the forge's API[5].
  • A forge that is down can be neither displayed nor instructed from Gaia. Gaia lists it from the registry, says that it is down and offers to start it. The CLI still writes to the store with no Hephaestus running.
  • A warning reaches only someone looking at Gaia. With Gaia closed, a forge that is off after a crash would sit in silence, so the CLI shows it too (section 3.4).
  • Conversations with hosted agents need nothing new in the forge. A message to an intake or a pipeline setup session is a command that exists (job-message), a picture goes up through the upload route that exists (for an intake session only, as today), and the agent's output is the job stream.

9Kept possible, not built

For a team sharing one forge through a remote store, each member's forge would work the tickets allocated to it, in full, and each member's Gaia would show their own forges. An allocator (Zeus) would decide the allocation. To keep that possible, the design carries four small seams and nothing more:

  1. The contract's outside face is made of commands, documents and a subscription, so a remote adapter is a client of an API.
  2. A ticket can carry which forge runs it, defaulting to the one forge. Zeus is whoever writes that field.
  3. Landing stays one step with a compare-and-swap contract. Forge's git code makes no fetch, pull or push call today, so landing is local; nothing else may assume a local main line.
  4. A forge's own capacity is a fact it can publish.

Left out on purpose: claiming and leases between forges, a merge queue, identity and permissions, schema migration of a shared store, relaying live agent output, offline work, and the redesign of Hephaestus's pass that a remote store needs (section 4).

10What is removed

  • From Hephaestus: BrowserSessions and the session routes, the Bridge bundle build, the render service's HTML, the Flint brain files. The server, the command route, the event broker and the monitor stream stay.
  • From the CLI: forge open, the progress.html stub, and the oversee verb, whose lifecycle verbs move to the top level beside start.
  • From the system: the Bridge as a program, and the embed machinery between Gaia and a Bridge (the iframe, session codes, the message channel, the frame-ancestors records).
  • From packages/: design-system, flint and brand, which become libraries of Gaia's page.
  • From practice: hand-editing a stored record.

12Open items and risks

To decide

No question of behaviour is open. What follows an ending on a network outage is decision 35, the bound of an install line is decision 36, and how a user changes a committed ticket is decision 48: it is put back into draft, edited there and committed again by the path any draft takes.

Risks

  1. The lease can stop a healthy forge's agents unless every condition of section 3.2 holds. It is the riskiest single piece.
  2. The lease renews only on progress, so a slow pass looks hung. A pass that waits through a merged-tree gate, for up to its 15 minutes, would stop the board's agents after a minute; the pass hands every gate line to Talos and carries on, and every synchronous step is bounded well below the lease.
  3. Recovery on instruction reverses tested behaviour and stalls where today's forge carries on. Which interruption causes wait is listed in section 7.
  4. The start classification misreads common cases (section 7).
  5. A half-finished landing. The trace exists and found every step safe to redo or detectable as done but three, the landing journal line, the release cleanup and the tip restore before freeSlot's hold, which reconcile must cover (stage 0 plan, table B).
  6. A failed pass is not a crash. A pass that fails on a held lock is retried today, and with the CLI, Hephaestus and agents all taking the lock that happens more often. It needs a name of its own.
  7. The store port has one adapter, and its command face cannot carry Hephaestus's own pass.
  8. The contract package holds 9 of the 76 command kinds. Stage 4 adds the board's kinds and its documents with types of their own, so the contract repeats the shape of forge's model, and a view that moves in stage 6 may still find a fact it needs unserved.
  9. Stage 6 is far larger than a move suggests.
  10. A forge that is down shows nothing but its name in Gaia and takes no instruction from it.
  11. The other platforms. Linux and Windows adapters exist, with no real-system recordings.
  12. One Talos is one point of failure for a board.
  13. The outage signal is only partly public. No session that ended on an outage has been recorded; the signal is read from the schemas inside Claude Code 2.1.326. The field that says the host could not be reached is marked internal there and may change with a version. A plain timeout carries no typed kind and looks like any other failed result, and the result line alone does not prove that retries ran out. What Talos does not recognise goes down today's failure path.
