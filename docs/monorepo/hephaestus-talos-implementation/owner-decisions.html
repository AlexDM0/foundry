Owner decisions

Every decision the implementation plan of Hephaestus, Talos and Gaia leaves to the owner: 71 in 7 stage files, and 14 more the plan refresh raised. Each has a recommended default. Answer here, then copy the JSON at the bottom. Answers live only in this page until they are copied or downloaded.

The two open items of the design, what follows an ending on a network outage and a time bound for an install line, are asked once, under stages 0 and 1. The 6 later items that only point back at them are left out.

Stages 0 and 1 stage-0-1-trace-and-base.md

S0-1.1

What the forge does after an agent ended on a network outage

Resume by itself, which needs a reachability probe on a real-time interval, or wait for an instruction. Recommended default: wait for an instruction, with one instruction to resume every job that ended this way, since it matches decision 13 and needs no probe. Stage 2 builds what both answers share: the recognised ending, its own end reason and cause, never counted as a crash or a failure.

Stage 3 stage-3-presence-recovery.md

S3.3

What a crash suspected before a reboot does

Built here: the classification flags it, a crash log is written and marked suspected, and the flag is shown. The fork: keep the forge off as after a crash, or serve with a warning. Recommended default: serve with the warning, because a sleep that ends in a dead battery reads the same and would otherwise keep the forge off after a harmless shutdown.

Answer for S3.3
S3.4

Whether an unexpected error in a pass is a crash

Built here: pass-abandoned with the reason unexpected-error, retried, counted, and a notice after three in a row. Recommended default: keep it a notice in this stage; if the owner wants decision 14 applied to it, the change is to stop after the third and write a crash log.

Answer for S3.4
S3.5

What an instructed resume does to the crash count

Recommended default: an instruction sets crashResumes to 0, so a job the user resumed gets two automatic resumes again before it waits.

Answer for S3.5
S3.6

Whether a retried merge, refresh or constitution commit after a waiting start waits too

Built here: all three wait after a crash, reboot or stop, and keep today's retry while the forge stays up. Recommended default: as built, adjusted to stage 0's trace of what an Airlock leaves half done.

Answer for S3.6
S3.7

Whether the verb is resume

beside oversee resume, which undoes a pause. Recommended default: keep resume for interrupted work and keep the pause pair, told apart by help text; stage 9 renames the pair to hephaestus pause and hephaestus resume with the rest of the verb (stage 9's replacement table). The alternative, renaming the unpause verb (for example to continue), is a change to stage 9's table and its command kind hephaestus-resume.

Answer for S3.7
S3.8

How Gaia learns that a forge that is down crashed

The design has Gaia watch presence (section 8) and run the CLI only to start, stop and set up a forge (section 3.4); a down forge serves no API. Built: a presence key in the machine registry's entry, written at a start, a stop, a handover and a refused start (WP3.8), which Gaia reads with the rest of the registry. A crash itself writes nothing, so until a start classifies it Gaia sees serving with a dead process. Recommended default: as built; stage 6 (WP6.21) reads that as "down".

Answer for S3.8
