Entities: one forge for a monorepo

How one forge at the root of a monorepo gives every app and package its own constitution, pipeline and agents, with one intake and one board. A forge in a single app, and a forge on a plain repository, stay as they are.

01

Only in a top-level forge

Entities exist when a tracker at the repository root names them. Folder forges and plain repositories keep today's behaviour.

02

One concept: the entity

An app, a package or the root. Each owns its folders, a constitution, a pipeline and agent settings.

03

One job, one constitution

Every builder and reviewer works under the rules of exactly one entity and writes only that entity's files.

04

A border is crossed in stages

The app's builder proposes the package change. The package's builder implements it, the package's reviewer reviews it, then the app catches up and is reviewed last.

05

Intake splits by entity

A strong model at the front door routes a request to entities and files a ticket for each, ordered and prioritised.

06

First make today's guard real

The reach check exists in the code but no production caller switches it on. That comes before anything new.

The strategy in one paragraph

A ticket belongs to one entity. When its work needs a change in a whitelisted package, the ticket runs in stages on one branch, one job at a time, each job under its own entity's constitution, and lands as one change. A need outside the whitelist becomes a ticket of the other entity, and the first ticket waits on it. A ticket that stays inside one entity runs exactly as today.

The full text is strategy.md beside this page; the functional brief for the pipeline builder is pipeline-builder-monorepo-mode.md.

The guard is written but not connected

Customs holds the reach check, and a spec covers it, but the place that builds the Customs subject for a builder or reviewer passes no project scope, so the check returns "passed" before looking at a single path. Two related holes sit beside it: the instruction-file check receives project paths where it expects repository paths, so for a folder tracker a builder's change to its own constitution would not match; and the merge step calls only three checks by name instead of the whole column for its role.[4][5][6] Everything below assumes these are closed first.

Scope: three configurations

The first iteration rejected a root tracker with a package scope per ticket, because it gave no Overseer or Bridge per package.[1] This iteration adds that shape beside the folder forges instead of replacing them.

The model

3.2 Ownership

  • Every tracked path has exactly one owner: the entity with the longest home folder that contains it, else root.
  • .forge/, .claude/ and .mcp.json at any depth stay protected from every agent.
  • Entity size is the release valve. A border costs stages. A package private to one app is a further home folder of that app's entity, not an entity of its own.
  • The root entity is an ordinary entity for tickets. The owner may give it gates and a constitution. Nobody can whitelist it. Without gates it is for a person, as the root of this repository is now.

3.3 Ticket

  • entity: required to ready a ticket in a top-level forge. The product owner assigns it, at intake and, after a first Apply in monorepo mode, to every pending ticket without one; it asks the owner when it cannot tell (E81). The owner assigns none. The CLI verb, which the product owner runs, is ticket entity.
  • crosses: optional list of whitelisted packages intake expects the ticket to cross into. A forecast for the board; what the branch really changed decides the stages.

3.4 Job

  • A job gains entity (whose stage it runs) and stage. Its constitution, instruction list, model, effort, gates, prepare steps and toolchain grants all come from that entity.
  • A session starts at the worktree's root, as a root tracker's does today. Its prompt names the folders it may change. Starting inside an entity's folder would cut off the lockfile and the root's settings, skills and CLAUDE.md.
  • The session's Edit and Write rules list only the folders the stage may change. An edit elsewhere is denied at once. Bash is not stopped there; Customs judges what the job left.

Lifecycle of a ticket

The problem in one sentence: an agent building a Gaia ticket that edits packages/design-system works under Gaia's rules and has no reason to know the package has its own. The answer is not to teach the app's agent the package's rules. It is to let the app's agent say what it needs, and let the package's own agents write and judge what lands in the package.

4.1 A ticket inside one entity

Build, review, landing, as today, with the entity's constitution, pipeline and agents.

  • What starts the stages. After stage 1, Customs sorts the paths the branch itself changed past its target by owner. Home and reach: nothing more. A whitelisted package: stages 2 and 3 for it. Anything else: refused (E11).
  • Several packages. Stages 2 and 3 run once per package, one package after the other, a package before the packages that depend on it.
  • The seal. At the end of stage 3 the Overseer stores a hash of the ticket's own change to the package: the difference, on the package's folders and on the reach paths a package stage changed, between the target and the branch, with the target's merged-in commits left out. This is how Customs already judges a branch against its target. Later jobs of the ticket may not alter that change. A merge of the main line never breaks a seal.
  • Skipping adapt. When, for every crossed package, the package's builder reports that what the package exposes is unchanged from the proposal, and the package's reviewer confirms it, stage 4 is skipped. When stage 4 runs, it resumes the stage 1 session if it can.
  • Ticket status. A stage job never moves the ticket's status. The ticket is in-progress through stages 1 to 4 and in-review in stage 5; the Playbook launches by the row's stage, not by the status.
  • Counters. Red handoffs and failed passes are counted per stage and entity and start at zero when a stage starts. Today's bounds apply within a stage.
  • Review. One bar per review stage, labelled with its entity. Rounds are numbered per stage, so the home review's round 1 is its first whatever the package review needed.
  • Handoff and Acceptance. ## Handoff has one part per stage that built, and a stage replaces only its own part. The evidence for the ticket's Acceptance is owned by the last home build stage: stage 4, or stage 1 when stage 4 was skipped.
  • Questions. A question from any stage's agent goes to the owner, as today.

4.3 A need outside the whitelist

  1. The agent of a build stage declares the need through its Hatch before it writes there: the entity, a title, a numbered Acceptance that holds the intended use, and a Brief. An incomplete need is refused back to the agent.
  2. Its job ends with the outcome needs-declared. The branch and its commits stay.
  3. The Overseer files the ticket for the other entity, stamped filedByJob, and submits it. With ticket review off it is pending; with it on it waits for the owner like any ticket, shown as blocking the first one. The first ticket gets it in dependsOn. The new ticket does not wait on the first.
  4. The first ticket keeps its status, its stage, its seals and its counters. The Playbook launches nothing for a ticket with an unsettled dependency.
  5. When the dependency is delivered, the stage that declared the need runs again: the main line is merged in, and the session is resumed, or a fresh one starts with the earlier notes.
  6. Priority. The need's ticket runs at the highest priority among itself and the tickets that wait on it, also when one of them is raised later.
Why this order
  • The proposal is a working use. A change that already runs against the app is a better specification than a description written before any code, and the app's builder finishes its work in one go.
  • The package's law holds. Every package line that lands was written or accepted by a builder under the package's constitution and then reviewed under it.
  • The reviews are staggered. The package is settled first, the app is brought in line with the final package, and the app's reviewer looks last, so its review covers the seam.
  • One job at a time. Forge reviewers fix what they find and commit on the ticket's branch.[22] In sequence, no reviewer changes code another has already judged.
  • One branch, one landing. The package change never reaches the main line without its consumer.

A pipeline per entity

Which gates run, and when

  • Per stage. A stage ends with the gates of its own entity, run from that entity's pipeline with that entity's toolchain.
  • At landing. On the merged tree the Airlock runs the gates of every entity the ticket changed, and of every entity that depends on a changed one, so a Gaia ticket that changes the design system cannot turn forge red unseen.
  • Deduplicated. Prepare steps are merged on command and folder, not on name; one bun install at the root serves every entity.
  • Tool-agnostic. Gates stay plain commands and forge keeps knowing no build tool. Where a repository has a cache such as Turborepo, a whole-repository gate line per entity remains valid and makes untouched work a replay, as now.[1]

Landing

  • A top-level forge has one Airlock train per target, with today's ordering by priority and predicted conflicts.[15]
  • The dispatcher can prefer tickets on disjoint entities, which rarely conflict; today the Overseer knows nothing about files and relies on filing-time ordering.[12]
  • A conflict is resolved under the constitution of the entity whose files conflicted, and re-reviewed by that entity's reviewer.
  • Later optimisation: skip a re-gate after a landing that touched nothing in the ticket's entities or their dependencies. It trusts dependsOn, so it stays off by default.

Protection that must not weaken

At the repository root only the root's .claude folder is denied to agents today; a folder tracker adds its own.[7] A top-level forge must deny .claude and .mcp.json in every entity home, in the sandbox and in Customs, or an agent could rewrite an entity's rules.

Intake: one front door, split by entity

In a top-level forge one product owner serves the whole repository, and it is where the strongest model pays off: a good split at the front means few borders are discovered later. It receives the entity map (keys, folders, summaries, whitelists), not the constitutions, which it does not get today either.[11]

  1. Route. Name the entities the request affects.
  2. Split by entity, then by mechanism as today.[12] A package change that stands on its own (a new component, a changed contract) is a ticket of the package.
  3. Mark the crossings. Where an app ticket needs a small supporting change in a whitelisted package, the ticket names that package, and it will run in stages.
  4. Order and prioritise. dependsOn when the package ticket can land first; a group when tickets must land together. Both exist.[10] Priority orders the ready tickets, as now.[3]
  5. Refuse early. Filing refuses a draft that names files of an entity outside its own and its whitelist, before any agent runs.

What intake misses, the builder finds: a crossing into a whitelisted package simply adds the stages, and a need outside the whitelist becomes a ticket the first one waits on. A ticket created that way inherits the priority of the ticket that needs it, so urgent work does not queue behind routine work.

Monitoring

  • Bridge. The entity becomes a dimension beside the epic: a filter and swimlanes on the Kanban, an entity chip on every ticket, the stages of a crossing ticket with whose turn it is, the pipeline view per entity. The merge queue stays one list per target.
  • Gaia, top-level forge. Still one forge; the monitor snapshot gains the entities. Added keys ship as a minor version, and Gaia, which supports one forge version, adopts it.[13]
  • Gaia, folder forges. The registry entry gains the repository root and prefix, already planned,[1] so Gaia can show the forges of one repository together.

If the commit failure needs explicit grants: what a commit writes, and the hazards

A commit in a linked worktree writes the worktree's admin folder (index, HEAD log, message file), new loose objects in the shared object store, and the branch's ref with its lock file and log.

  • Write access to the object store includes deleting objects, which no ref check would notice.
  • The ref and its .lock sibling must be named exactly; a pattern such as ticket-014* also matches ticket-0140.
  • On Linux a path that does not exist yet cannot be granted, so a whole folder would have to be, and prevention becomes detection after the fact.

Gate sandboxes receive the admin folder only.[5] This is why the probe comes before any widening.

A top-level forge starts its sessions at the worktree's root, where a root tracker commits today, so it does not depend on the outcome of the commit probe.

Implementation

The order is the order to build in. Each step keeps bun run verify green. A forge without entities must stay as it is after every step: every new git call sits behind an early return when the pipeline has no entities, the way changesStayInHomeAndReach returns before git for a root tracker.

For this repository

Step 0 fixes the two folder forges as they are. Whether forge and Gaia then become one top-level forge is a separate choice: it gives the design system's constitution force, shared intake and tickets that wait on each other across apps, and it costs a board reset, since the trackers must be cleared and set up at the root.

Risks and open decisions

RiskWhy it mattersAnswer in this strategy
Building on an unwired guardEvery scope rule here sits on a check that does not run yet.Step 0, before anything else, with a spec that fails when a real builder subject carries no scope.
Cost of a crossingFour sessions, five with the adapt stage, one after the other, against two for a ticket inside one entity.Only crossing tickets pay. Keep borders few through entity size, split well at intake, skip the adapt stage when nothing changed. Count crossings and returns per entity on the board.
The package builder rewrites what the app needs awayIt knows the package's rules, not the app's goal.It receives the proposal and the app's use of it; the adapt stage catches a mismatch; one way back, then a decision.
A popular package becomes a queueSeveral tickets carry changes to the same package and re-review at landing.Merge order already prefers clean merges; a package under that pressure is better served by its own tickets, which intake can file.
New ticket statesStages add states to the Playbook and the board.A single-entity ticket is the one-stage case and must replay exactly as today; hold that with a frozen spec like the root tracker's.
Weaker protection at the rootNested .claude folders become writable in a top-level forge.Deny them in every entity home, step 2.
Half the throughputOne board at two agents replaces two boards at two each.Raise the board limit and add a cap per entity, step 6.

Decisions

The owner decided on 16 November 2026:

  • adapt is skipped when what the package exposes is unchanged from the proposal. The package's builder states it in its report, and the package's reviewer confirms it.
  • Stage 4 resumes the stage 1 session when it exists, and starts fresh otherwise (E43).
  • A top-level forge keeps today's default concurrency. An entity's cap sits under it.
  • This repository moves from two folder forges to one top-level forge, as the last step of this work.
