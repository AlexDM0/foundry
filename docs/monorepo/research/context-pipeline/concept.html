A pipeline of steps over one context

The proposal: a pipeline starts at a trigger, and every step after it reads from a shared context and adds a named artifact to it. Forge after the rework is one hard-wired instance of exactly this, which is the best argument for the idea and the sharpest test of it.

What the idea gets right

What a step is. Forge already keeps an ordered list of what each agent reads, for seven fixed roles.[6] The idea removes the word "fixed".

What the brief leaves out

What accepts a step's output, and where the work goes when it is refused. Forge's guarantees live in those two slots.

Where it lands

Make steps data. Keep verification, bounded ways back and the landing as code. Choose step kinds from a closed catalogue, as the brief already does for triggers.

01The concept

Five words from the brief[1], each with the sharpening it needs before it can carry forge.

WordIn the briefSharpened
TriggerA ticket creation event, or a ticket input that became available from an outside source. Triggers are preconfigured and selectable.A member of a closed catalogue, built in code. It ends by putting ARTIFACT_TICKET into the context.
ContextWhat a step takes in: the constitution, the repo as a whole, any doc, any external reference, an agent description, an instruction, or an artifact.Per ticket, the set of items that exist so far. A step declares which of them it reads. Items differ in how they are referenced (see below).
ArtifactThe named output of a step: ARTIFACT_TICKET, ARTIFACT_SPEC, ARTIFACT_PLAN.A document with a type, a version and a record of the versions it was made from. A repo ref is not an artifact: it moves.
StepTakes context, runs an agent with an instruction, may need a chat interface, may be picked up by people with given roles, emits an artifact.Seven slots, drawn below. The brief fills five.
Sign-offA request to a team member at the end of a step.One kind of acceptance. For a document it is the only check there is, so it is part of the step and not an extra.

Who

The team roles that may pick the step up: B, C, D. Nobody, when the step runs by itself.

Where the session stands: a worktree at a ref, a folder of its own, or nowhere in the repo.

Ends when

The person closes the chat, or the session reports that it is done.

Accepted by not in the brief

What turns the output from a claim into a fact: a shape check, gates, a check against git, a person's sign-off.

Way back not in the brief

Where the work goes when acceptance fails, whether the same session resumes, and after how many tries the ticket stops and waits for a person.

The plan step of the brief, laid out by slot. The two slots at the bottom are the ones forge's own rules demand of every step it runs today.

A context item is referenced in one of three ways

"The repo as a whole" and "ARTIFACT_SPEC" are both context, and they behave differently. Forge already treats them differently, without naming the difference.

ReferenceMeaningWhat forge does today
PinnedThis exact version of a document.A builder's ticket body must be unchanged since its launch, or Customs refuses the run.[3]
TrackingWhatever the main line holds at the moment the session starts.The constitution and every tracked instruction file are read from the main line at each launch and each resume, never from the ticket's branch.[8]
Working copyA place to stand and change, not a text to read.A worktree on the ticket's branch, cut from the target's tip.[3]

Written rules and decisions it touches

Rule or decisionWhat the concept does to it
"The forge follows a fixed, programmed workflow, and the user is a step in it." Decision 11 of the rework.[5]Changes the first half. The workflow stays programmed and is never improvised, but it is fixed per board by its definition, not once for every forge. A numbered decision, so it needs the owner's word.
"The forge cannot ask the user anything by itself." The same decision.[5]Holds, if a chat step starts when a person picks it up, and a sign-off request is a recorded wait, as a question is today.
A committed ticket's content is fixed and kept by content hash. Decision 48.[5]Becomes the general rule. Accepted means fixed; a change means back to draft and accepted again.
The constitution commit is the one tracked write of forge to a main line outside a ticket's landing.[21]Holds, if an artifact is either a record of the forge or a file on the ticket's branch that lands with it. A spec written to the main line before its ticket lands would break it.
A tracker with no entities asks git exactly what it asked before, held against a frozen table.[21]Holds, and gets harder. The baseline definition has to reproduce today's calls one for one.
Internal values are string-literal unions, never display text.[21]Bends. A step's name is a board's own text. The state of a step can stay a fixed union.
Identity and permissions are left out on purpose.[5]Holds, if roles are labels that route work and nothing more.

What it makes possible

  • Thinking before building. A spec and a plan, each accepted, before a builder spends a token. Today the only document before the build is the ticket, and the first judgement of the work comes after it is built.[3]
  • Steps forge does not have: a design step, a security review, a test plan, release notes. Each is a definition, not a release of forge.
  • Different paths for different work. A typo and a new subsystem need not pass the same steps.
  • Work that starts outside forge. A ticket that begins in another system and still passes the same checks.
  • A unit to hand to a person. "This step, for someone with role B" is something a team can allocate. A whole ticket is too coarse.
  • Replay. A step with declared inputs at known versions can be run again under another configuration and priced, which the compounding research asks for.[20]

08Where this lands

The steelman survives only in a narrow form, and the narrow form is worth building.

Code · never configured

The kernel

  • One driver moves work
  • An output is a claim until checked
  • Ways back are bounded, counted from the log
  • Landing is a compare-and-swap
  • Slots, budgets, write scope
Code · selectable

The catalogue

  • Trigger kinds
  • Step kinds: conversation, agent work, sign-off, code
  • Artifact types, each with a shape
  • Kinds of acceptance
  • Kinds of way back
Data · per board or entity

The definition

  • Which steps, in which order
  • What each reads: its context
  • Agent description and instruction
  • Who may pick it up, who signs
  • Which steps a ticket may skip

The brief already takes this position for triggers: they are "preconfigured as selectable".[1] The same rule for step kinds, acceptance and ways back is what separates the steelman from the strawman. A board composes from parts that forge knows how to verify; it does not invent parts.

The baseline requirement becomes a test. The default definition is today's forge: intake, ticket review, build, review, merge approval, landing. A forge running that definition behaves exactly as forge does now. Forge already holds one behaviour this way: a tracker with no entities must ask git exactly what it asked before entities existed, checked against a frozen table.[21]

The order that costs least

  1. Name what exists. The ticket, the Handoff and each Review become typed artifacts with a version. The per-role instruction list becomes the step's context. Nothing behaves differently.
  2. Add document steps before a ticket is committed. Spec and plan sit where intake sits: before the stretch that runs without people. They reuse the conversation forge has for intake and the sign-off it has as ticket review. The path from build to landing is not touched.
  3. Make the path from build to landing a definition, behind the frozen baseline.
  4. Add outside triggers, one source at a time.
  5. Enforce roles when people have an identity, which is its own project.
