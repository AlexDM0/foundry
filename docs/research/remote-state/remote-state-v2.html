Shared state and many machines

Version 2 of the remote state research of 15 November, rewritten as a roadmap item: stage 5 of foundry's road to the agentic software factory. It states what the whitepaper asks of foundry here, where foundry starts, six milestones between the two, and what the owner has to decide. Nothing on this page is built or decided.

The whitepaper asks

One state, many machines

A factory state in the cloud, shared by machines that each run the Workflow Loop, anywhere. A fleet manager balances load across them and does nothing more.[11]

Foundry starts

One forge on one machine

Board state already passes through the BoardStore port, and the design keeps a team possible through four seams. Nothing remote is built.[1][3]

The gap

The pass, the names, the branches

Hephaestus's pass holds the store while it runs git, which no remote store can offer. No forge knows its machine, no ticket knows its forge, and no branch leaves the machine.

Two rules hold through every milestone. An agent's output is a claim, and only a loop turns a claim into state: that is v1's rule, and Customs and the gates enforce it today. Several machines add a second one: only one loop works a ticket at a time.

v1 asked how one Overseer could keep its state in a remote database and drive cloud Claude Code sessions as workers. The whitepaper asks for a different shape, and foundry's own design of 18 to 21 November already sketches it: each member's forge works the tickets allocated to it, in full.[3] So v2 keeps v1's findings on the database, the login and the trust boundary, parks its cloud workers, and puts the redesign of the pass first. The last section lists what changed.

The whitepaper leaves three things to this item: how code moves between machines, what a machine does when the factory state cannot be reached, and which state stays in a company system such as Jira. The last one is stage 4's question; the first two are decisions below.

Where foundry starts

Read from the code on 23 November 2026, at commit 0f1e760f. Since v1 the Overseer became Hephaestus, the Watchers became one Talos per board, the Bridge went away for Gaia, and the store port that v1 recommended was built.

What is stored, and what would be shared

PathHoldsKindBehind the portIn a shared state?

How it works now

  • One port for the board, with three faces. Commands, which a CLI verb, the Hatch and the HTTP command endpoint all reach through one service; a board transaction for Hephaestus; and reads that take no lock. There is one adapter, on local files, and a contract spec that any other adapter must pass.[1][4]
  • The pass is not made of commands. Hephaestus changes the board inside one hold and runs git inside that hold. The port says so itself: the write is exclusive "an await and a git call inside it included; a remote adapter cannot offer that".[1]
  • A lock that passes only from a dead holder. The write lock is a folder of generation records; another writer takes it only when the holder's process is gone. A hold journal is written first and replayed by the next holder.[2]
  • No write names what it read. The store's revision is a hash for readers. Nothing compares versions on a write, because the lock makes that unnecessary on one machine.[1]
  • Nobody edits a stored record by hand. An edit of a ticket is a command, refused once the ticket is committed.[3]
  • The CLI writes without Hephaestus. Outside a job a verb writes in process and then nudges Hephaestus; under a job it is relayed through the Hatch.[5]
  • Wake-ups come from the filesystem. A 150 ms debounced watch of the data folder and the Hatch folders, a 30 second sweep, and the nudge.[5]
  • Children are local by construction. Hephaestus reaches Talos over a Unix socket or a named pipe and reads its records and event logs from disk. BoardChildren is the one interface to them, with one adapter.[5][6]
  • Git never leaves the machine. Forge's git code makes no fetch, pull or push call, and push is a denied command for a worker.[3][5]
  • No person and no machine has an identity. A forge binds to 127.0.0.1 and takes one bearer token, made fresh at each start. Roles in the context pipeline design are labels: "Nothing enforces it, and no login is part of this design."[5][9]

The target

Each machine runs the whole loop for its own tickets. The board's records sit behind one forge that owns the database. Code moves between machines only through the code host.

Three rules of the target

  • One loop per ticket. A ticket names the forge that runs it. That forge works it in full: build, gates, Customs, review and landing. No other loop touches it until the allocation changes. Deciding stays a pure function on one machine, so the loop stays deterministic.
  • One writer of the database. Every machine is a client of the state forge and holds a credential of its own. A session holds none, as today: the Hatch folder is its only way in, and the sandbox on each machine is unchanged.
  • One road for code. A ticket's branch leaves a machine only by a push to the code host, and landing is a compare-and-swap there. No machine reads another machine's disk, and no forge talks to another forge.
Where v1 and the design agree. v1 concluded from the security side that the Overseer should reach a backend of your own and never the database. The design reached the same from the validation side, and names the backend: a forge. That removes a second implementation of the command kinds, which a separate backend would have needed.

Milestones

Six steps, ordered by what each needs. The first two change nothing outside one machine and need no decision about hosting. The order and the sizes are Claude's proposal.

  1. Split the pass Large

    AddsHephaestus's pass no longer holds the store while git runs. Every change the pass makes becomes one of two things: a command, or a step in two parts where the store records the intent, git settles it, and the store records the outcome. A restart resolves an intent that has no outcome by reading git, as reconciliation at start does today. A write also names the revision of the ticket it read.

    User seesNothing, and that is the test: everything passes on local files.

    Why firstThe design names it as the one thing a remote store cannot do without: "A remote adapter cannot carry a hold that spans a git fast-forward; the remote future needs that pass redesigned, which this plan does not do."[3] It touches landing, ending and interrupting a job, incidents and the Hatch inbox. The roadmap calls this the second decision on the road.[12]

  2. Name the forge Small

    AddsA forge gets an identity that says which machine it is. It publishes its capacity: its agent limit and what is in use. A ticket carries the forge that runs it, defaulting to the one forge. These are seams 2 and 4 of the design; Claude found no field for either in the tracker model or the contracts.

    User seesGaia can say which forge works a ticket. With one forge that is always the same answer.

  3. Shared state Large

    AddsThe state forge: a forge whose store adapter is a database and whose API is reachable beyond loopback, over TLS. A remote adapter that passes BoardStore.contract.spec.ts. Enrolment of a machine at init, which gives it a credential. A subscription to changes in place of the file watch, with the sweep kept as the fallback. A stated behaviour when the state cannot be reached, and an export back to local files.

    User seesThe board survives the loss of the machine. Gaia on a second machine shows the board, read only. Still one loop: one machine works the board.

    NeedsMilestone 1, and the owner's answers on where the state may live and who may enrol a machine.

  4. Branches travel Medium

    AddsForge's git code learns to fetch and to push. A ticket's branch is pushed when its phase ends. Landing merges and gates the merged tree on the machine, then pushes a fast-forward that the code host refuses if the main line moved; a refusal starts the landing again. A worker still may not push.

    User seesTicket branches and merges on the code host.

    NoteThis reverses a deliberate rule, that git never leaves the machine. Stage 4 needs the same code for pull requests, so it can be built there or here, once.

  5. Two machines, one board Large

    AddsA forge works only the tickets allocated to it. Until a fleet manager exists, allocation is a claim: a forge with room takes a ready ticket, and the state forge lets the first claim win. The merge order becomes one queue in the shared state. The board's concurrency limit becomes the factory's, beside each machine's own. An allocation is a lease, so the tickets of a lost machine surface. A machine on another forge version is refused and told to update.

    User seesA second machine started on the same board picks up ready tickets. Gaia shows which machine works what, and an approval can be given from either machine.

    NeedsMilestones 2, 3 and 4. This is where the design's "left out on purpose" list is paid: claiming and leases between forges, and a merge queue.

  6. Fleet manager Medium

    AddsThe allocator, Zeus in the design: it reads the published capacities and writes the allocation field, and nothing more. A recipe for a cloud machine: install, enrol, start, with billing by API key and a budget. A default capacity of the core count minus one, which is the whitepaper's core reserved for the loop.

    User seesMore machines mean more tickets in flight, without anybody assigning them.

What this item does not build. Identity of people, permissions, a personal dashboard per team member and governance above the factory are stage 6. Milestone 3 enrols machines; it gives no person a role.

Decisions

The first list is the owner's: how the system behaves. Each carries Claude's recommendation. The second list closes questions v1 left open. Mechanics such as the database product, the token store and the feed's transport are the build's to choose.

Carried from v1

These findings still shape milestone 3. They stand as read on 15 November 2026 and were not opened again for v2.

The database is a low-stakes choice

Behind the state forge the store needs little: one board's records, appends to a log, a guarded write per ticket and a feed of changes. MongoDB Atlas does that on its free or Flex tier.[14][15][37] So would Postgres or SQLite beside the state forge, which is Claude's lean: fewer parts, and nothing of a client's leaves the machine that hosts it.

No machine connects to the database

Atlas takes identity-provider logins only from M10 up, GitHub issues no ID tokens for users, a roaming laptop meets the IP access list, and access control stops at the collection.[16][17][18][19] All four fall away behind the state forge.

Alternatives worth knowing

Supabase has row-level security and GitHub login built in. Turso keeps a local replica that syncs, the closest to today's files. A Cloudflare Durable Object per board is single-threaded, which removes the lock.[20][21][22]

Enrolment through a GitHub login

Loopback redirect with PKCE by default, the device flow only for a machine with no browser.[23][24][25] The state forge checks the person's permission on the repository and issues the machine a short-lived credential.[27] No connection string is copied to a machine.

One process refreshes

A GitHub App user token lasts eight hours; each refresh replaces the refresh token.[26] Two processes refreshing at once strand one, so the remote adapter owns the credential for the CLI and Hephaestus alike. Bun's secrets API is new and experimental.[28]

The sandbox is still the boundary

A session can write its worktree and its Hatch folder, and gets a five-name environment plus the Claude login. The machine credential must never join that list, and gate confinement must deny it too.[5][6][7]

A compromised machine can still lie, and now it lies to the team. On one machine a false gate verdict harms its owner. On a shared state the state forge accepts each machine's verdicts as it accepts its own. The landing gate on the merged tree still runs, but on the machine that holds the ticket. If a machine may not be trusted, the final gates belong on a runner no agent touched: the remote CI of stage 4.
Windows has no confinement. Sessions and gates run unconfined there by design.[7] On Windows a session can reach whatever the loop can, the machine credential included. See the decisions.

Parked: cloud sessions as workers

v1's third question was how one Overseer could run jobs as cloud Claude Code sessions. This item does not build that.

  • It is not the whitepaper's machine. The whitepaper's machine runs a loop: it gates, verifies and lands on its own. A cloud session is a worker with no loop beside it, so every check would still run on the machine that started it.
  • A daemon cannot follow or stop one. v1 found no event stream and no stop for a session started with claude --cloud; a follow-up is queued and not awaited, and completion needs a Stop hook that calls a public endpoint.[29][31]
  • The terms need an answer first. The Consumer Terms forbid automated access except where Anthropic permits it.[36] A loop that starts and steers cloud sessions all day goes further than the documented example.
  • A machine you run gives the same reach. A cloud machine with forge on it is "in the cloud" in the whitepaper's sense, keeps Talos, the sandbox and the gates, and needs nothing from the vendor beyond what a laptop needs.
